# Roadmap

This file documents possible future improvements. Items here are proposals, not current functionality and not a commitment to a specific release date.

## Customizable notifications

### Current behavior

Smart Entity Timer 0.1.3 can send notifications to configured compatible Home Assistant notification targets, but the title and message wording are generated by the integration and are not user-editable.

### Proposed future behavior

A future backend release may allow optional customization while keeping the current messages as safe defaults.

Suggested configuration:

- completion notification title;
- completion notification message;
- error notification title;
- error notification message;
- skipped-during-restart notification title/message;
- optional manual-cancellation notification title/message;
- optional automatic-cancellation notification title/message.

Simple placeholders could be supported, for example:

```text
{timer_name}
{target_name}
{action}
{duration}
{result}
{reason}
{finished_at}
```

Example:

```text
Title: A/C timer finished
Message: {target_name} was {action} after {duration}.
```

The first implementation should prefer simple documented placeholders instead of unrestricted templates. This keeps configuration understandable and reduces compatibility/support problems.

### Lifecycle events for advanced users

A complementary future improvement would be to emit Home Assistant events such as:

```text
smart_entity_timer.started
smart_entity_timer.completed
smart_entity_timer.cancelled
smart_entity_timer.skipped
smart_entity_timer.error
```

This would let advanced users build completely custom notifications and automations without forcing every possible notification option into the integration UI.

### Design principle

Notification execution belongs in the backend integration, not in the dashboard card, because notifications must continue to work when no dashboard is open and after Home Assistant restarts.

## Other future ideas

Only add new functionality after the current stable integration/card behavior remains backward compatible. Card API v2 should remain the contract unless a future change genuinely requires a new API version.
